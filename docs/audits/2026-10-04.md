# Maintenance audit: 2026-10-04

This is a dated maintenance record. The [architecture](../../ARCHITECTURE.md), [domain glossary](../../packages/skill/skills/repochan/references/terminology.md), package guides, schemas, and CLI help remain the current contracts.

## Product stage and milestone

RepoChan has a published CLI, eight public packages, nine shipped Agent Skills, a complete website catalog, coordinated package checks, and an official website. The product is beyond initial scaffolding. The next useful milestone is trustworthy reuse: a developer can understand the domain, use a Source Starter without damaging it, preserve creative history, and distinguish a runnable output from a customized or accepted one.

This audit focuses on that milestone. The execution model remains **Core + Skill, sole CLI binding, BYO Agent, no embedded runtime**. A broad rewrite or another orchestration framework would add risk without resolving the observed failures.

## Scope and evidence

The audit covers package ownership and imports, protocol mutations and recovery, order transitions, deterministic repository analysis, image transport/authentication, encoded pixel outputs, Starter localization, preview lifecycle, installed Skills, documentation authority, and package delivery. It includes the official website's setup copy and all twenty Source Starter builds, plus the separate local Score Review utility.

Findings were checked against current source and isolated fixtures. Repair acceptance uses actual files, decoded pixels, child processes, HTTP responses, and clean-room installation where relevant. Tests alone do not establish human visual acceptance, provider availability, or behavior on an operating system that was not exercised.

- The documentation index separates current contracts from proposals, design records, visual briefs, and README experiments. Retained records have visible context notices; obsolete local artifact links no longer masquerade as public references.
- Architecture and CLI guides describe current ownership and observable behavior. Package guides remove stale catalog counts and clarify original versus derived output.
- `test:documentation` checks source-backed links and installed-Skill reachability, including deleted tracked targets and multiple `srcset` candidates.
- `test:architecture` checks runtime manifests, the sole published bin, data-package entrypoints, static/dynamic imports, common `createRequire` forms, and relative cross-package bypasses. It is a deterministic contract guard, not a general security analyzer.
- The release-surface scanner reads Markdown documentation rather than interpreting binary image bytes as prose.

## Dependency security triage

The registry audit was checked on 2026-10-04. Workspace-wide counts include the private Astro build stacks in twenty Source Starters; they are not a count of independently exploitable CLI defects. The audit does **not** claim a clean dependency audit.

The CLI's image-edit dependency was upgraded from Sharp 0.34.5 to the pinned **0.35.4**. RepoChan decodes user-supplied files, so the [Sharp/libvips advisory](https://github.com/advisories/GHSA-f88m-g3jw-g9cj) and [Sharp/libheif advisory](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c) justify updating the actual pixel runtime. Its Node requirement is 20.9 or newer; CLI and image-edit manifests, setup documentation, and website copy now declare that minimum. The complete image-edit suite passed after the update, including byte-frozen output checks without changing expected hashes.

The independently locked official website received compatible transitive updates for devalue, js-yaml, nanoid, and PostCSS, without changing its Astro major or package ranges. Its production build still generated sixteen pages. Its registry audit reports decreased from fourteen to ten findings; the remaining ten include the unresolved framework critical finding and are not accepted as a clean audit.

Score Review's compatible Express 4/body-parser/qs updates resolve its separate registry findings: qs 6.16.0 includes the [published parser/serializer fix](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g). Its `npm audit --omit=dev` reports zero vulnerabilities after the update. That result applies to this small independent tool, not the monorepo or website toolchains.

The remaining Core runtime finding is [deeply nested brace-pattern exhaustion](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), through fast-glob and micromatch. Its current advisory has no patched version. Independent source review found one glob call, with the fixed pattern `**/*`; the project root is only `cwd`, and `.gitignore` is processed by the separate ignore library. A runtime probe with brace-containing paths and a deeply nested `.gitignore` observed only that fixed pattern and completed successfully. The advisory's external nested-pattern path is not reachable through the current Core walker. Keep this scope explicit; a future caller-controlled glob API would change the assessment. Replacing fast-glob with a native directory walk is a possible follow-up, with dot/ignore/symlink behavior preserved; an absent patch is not permission to invent a fixed version.

The [Astro AVIF optimization advisory](https://github.com/withastro/astro/security/advisories/GHSA-26w7-cxv4-gfx2) names 7.2.8 as the framework fix. That release [requires Node 22.12 or newer](https://raw.githubusercontent.com/withastro/astro/astro%407.2.8/packages/astro/package.json). Current Source Starters and the official site are static, without adapters, server rendering, or Astro image-optimization consumers; Browse builds a snapshot and serves its static `dist`, and the official deployment uploads only `dist`. The current public serving paths have no identified AVIF optimization entrypoint. Development servers still expose framework image functionality, so static output does not establish safety for every development-server usage. Maintain loopback development and static deployment boundaries.

The migration spans Astro 4/5 to 7, eight Tailwind integrations, and the current Node 20 build/deployment matrix. [Astro 6's migration guide](https://docs.astro.build/en/guides/upgrade-to/v6/) changes Node support and script/style order; [Astro 7's guide](https://docs.astro.build/en/guides/upgrade-to/v7/) changes the compiler and whitespace behavior. It needs production builds and visual acceptance across the catalog, rather than a version-range-only change. Framework version findings remain open.

## PR CI portability follow-up

The first PR CI run passed Linux quality on Node 20 and 24 and the build/pack acceptance, but Windows exposed a real Starter sync failure: Windows system tar rejects the GNU-only `--force-local` option. Both production extraction and fixture creation now invoke tar from the archive directory with a relative archive filename; extraction resolves its destination before changing the child process working directory. This supersedes the earlier workaround recorded in the changelog.

Real tar regressions cover spaces, leading-dash filenames, relative archive/cache paths, POSIX colon filenames, and damaged archives preserving the old cache and cleaning staging. Relative-path fixtures live on the checkout volume so the Windows test cannot silently become an absolute-path test across drives. UNC paths have argument-level coverage only. The targeted macOS suite passed 15 tests with the Windows-only npm check skipped; CLI lint passed. The updated PR must pass the native Windows CI gate before merge.

## Next: finite follow-up work

1. **Astro scaffold migration.** Upgrade the catalog and official site to a supported framework release, with the required Node and Tailwind changes, script/style-order checks, and visual acceptance. This is a framework migration across twenty websites, not a patch-level dependency replacement; see the security triage above.
2. **Brand derivatives in the Transfer Kit.** Several Source Starters consume ICO, Apple-touch, PWA, or social-preview files derived from an icon/banner but do not declare that dependency in their slots. Add an explicit derived-publication contract so one atomic apply updates all consumers and provenance. Reuse the existing image result; this is not a reason to commission more paid images. Until then, localized validation proves declared slots only, and completion reports must name untouched brand derivatives.
3. **Proof and source examples.** Source Starter gallery examples and other Starter previews may remain as clearly attributed source examples. Target-project claims require real target-project artifacts and provenance. A copied source Order ID is not target-project delivery evidence.
4. **Acceptance on other hosts.** Exercise native Windows process/file behavior and Linux headless opening in their actual environments. Mock platform branches are useful regressions, not substitutes for host acceptance.

5. **External provider follow-up.** The authorized Images API acceptance above now covers real generation, reference editing, native transparency, and recovery of a billed task. Live OAuth refresh and native Tasks submission remain untested. A known-job recovery function in image-gen with a thin `image recover` CLI binding is a bounded next slice; native Tasks submission requires its own verified request/size/transparency contract, rather than a path-only configuration change.
6. **Single-file publication.** Extend the no-clobber/stage-and-replace discipline to remaining direct image utility writers and generated-image replacement. Existence checks alone do not prevent a competing writer between check and save; direct overwrite can truncate old output on an I/O failure. Batch resize/slice publication and generated-image no-overwrite creation are covered by this repair; remaining direct replacement paths need the same publication discipline.
7. **Propagation through evidence.** Build a concise public showcase of reproducible happy paths, exact source/result attribution, and accepted localized sites. The cover and gallery improve first impression; durable proof is the next distribution asset.

## Later and deliberately outside this repair

Automatic downstream invalidation, remote catalogs, an orchestration/job engine, and a parallel MCP API are not needed for the failures above. Reconsider them only with concrete user demand and a domain contract. Source Starter design and human aesthetic acceptance remain creative work, not schema properties.
